# V2.1 roadmap — one GUI across multiple projects

V2.1 implements the multi-project experience described in
[docs/vision/user_flow.md](vision/user_flow.md#step-3--open-the-web-ui-window-cli).
It is intentionally separate from [the V2 roadmap](v2-roadmap.md): V2 settles the
deployment schema and routing model, while V2.1 changes the ownership and scope of the
daemon and Web UI.

The product name after V2 is **APM ProjectRunner**, typed as `apmpr`; commands and paths
below use that final name.

## Target experience

- One long-lived user service owns every registered project.
- `apmpr gui` opens one browser window without requiring a project path.
- The window lists registered projects and switches between them without relaunching.
- Initializing or registering a project makes it available in that list.
- Operations, events, credentials, desired state, and runtime observations remain
  explicitly scoped to one project.
- Closing the browser does not stop the service or any project instances.

## Work

### 1 — Global project registry

- [ ] Define the user-level state location and versioned registry format.
- [ ] Store a stable project identity, display name, and canonical workspace path.
- [ ] Register projects idempotently from `apmpr init` and
      `apmpr project register`.
- [ ] Detect missing, moved, duplicate, and inaccessible project paths with actionable
      diagnostics.
- [ ] Provide list, inspect, register, update-path, and forget operations without
      modifying adopted project contents.

### 2 — Multi-project daemon

- [ ] Replace the one-workspace daemon binding with a service that opens registered
      projects on demand.
- [ ] Require a project identity on every project-scoped API request, operation, event,
      and mutation.
- [ ] Keep per-project state, locks, generated artifacts, credentials, and operation
      limits isolated.
- [ ] Recover projects independently so one invalid or unavailable workspace does not
      prevent the service from starting.
- [ ] Define deterministic behavior when the same runtime resource appears to be claimed
      by two projects; never silently transfer ownership.

### 3 — Project switcher in the Web UI

- [ ] Add a project selector visible from every project-scoped screen.
- [ ] Show unavailable and invalid projects with their diagnostic instead of hiding
      them.
- [ ] Cancel or scope in-flight reads when switching so data from the previous project
      cannot appear in the new one.
- [ ] Preserve per-project navigation state without mixing project data.
- [ ] Provide register, locate moved project, and forget flows.

### 4 — CLI and service lifecycle

- [ ] `apmpr gui` connects to the user service and opens the shared window; it takes no
      project path.
- [ ] Service install, status, logs, and stop commands operate at user scope.
- [ ] Project-scoped CLI commands resolve an explicit project identity or the current
      project directory without starting another daemon.
- [ ] Migrate existing project-local daemon state without losing authored deployments
      or running-resource ownership records.

## Acceptance

V2.1 is complete when one installed service can:

1. Register two independent project folders.
2. Open one Web UI and switch between both projects.
3. Validate and run an operation in each project concurrently.
4. Stream events and show desired/observed state only under the correct project.
5. Restart the service and recover both registrations and their operation history.
6. Forget one project without changing its files or affecting the other project.

Multi-user collaboration, remote control planes, and syncing project registries between
machines are not part of V2.1.
